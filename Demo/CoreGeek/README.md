# CoreGeek —— 第一天（前 130 回合）解题说明

判题器通过 HTTP 下发每个回合的地图状态，本程序返回该回合的动作。
本解题只针对**第一天**：白天 70 回合 + 黑夜 60 回合。

## 运行

```bash
bash run.sh <port>               # 接口文档第 1 章的样例启动方式
python3 main3.py <port>          # 等价写法：监听 0.0.0.0:<port>，POST 任意路径即一次决策
python3 tools/smoke.py           # 离线迷你裁判器（进程内直调 decide），跑满 130 回合断言需求
python3 tools/mock_judge.py      # HTTP 级联调：把本程序当独立进程拉起来，走真实 socket 驱动 130 回合
```

响应固定为 `{"roleCommandMap": {...}, "prompt": "...", "executeCmd": "..."}`。

## 代码结构

| 文件 | 职责 |
| --- | --- |
| `run.sh` | 判题器启动入口（`bash run.sh <port>`） |
| `main3.py` | 命令行入口：校验端口、切换工作目录、加载 `agent.server` |
| `src/agent/protocol.py` | 解析 Request（含 `playerTasks` / `vendorShopList` / `llmResp` / `lastCmdResult` / 动作合法性），构造全部动作码 |
| `src/agent/grid.py` | 八方向栅格 A*：多目标寻路 + 路径长度估计 |
| `src/agent/memory.py` | 跨回合记忆；开局一次性算出基地几何布局（C 形护罩 / 3 个火箭位 / 3 个站位） |
| `src/agent/brain.py` | 策略本体：白天分工、自进化任务状态机、BOSS 采购、夜晚集火 |
| `src/agent/server.py` | `ThreadingHTTPServer`；任何异常都回空指令，保证进程不被打死 |
| `tools/smoke.py` | 迷你裁判器 + 断言（进程内调用策略） |
| `tools/mock_judge.py` | HTTP 级联调：真实进程 + 真实 POST，逐条校验接口文档并测时延 |
| `tools/diagnose.py` | 拿一份真实 Request 报文，逐条讲清楚「为什么某个角色没动作」 |

## 建造布局（需求给定的固定坐标）

记基地**左下角**为 `(x, y)`，则基地占 4 格：`(x,y) (x+1,y) (x,y+1) (x+1,y+1)`。

> ⚠️ 坐标口径：报文里 `station` 的 `pos` 是**左上角**（接口文档 1.3.1），
> 所以 `x = pos.x`、`y = pos.y - 1`。样例报文里 `station=(10,24)`，已有的三座塔在
> `(9,24)/(10,25)/(9,25)`——只有按「pos 是左上角」理解，这三格才都在基地外一圈；
> 若把 `pos` 当左下角，`(10,25)` 会落进基地里。差这一格整张图都会错位。
>
> 这个换算**只在一处**：`protocol.POS_IS_TOP_LEFT`（连同 `station_footprint()` 与
> `base_lower_left()`）。口径若再变，只改这一个常量，基地占格与整套布局会一起跟着
> 平移，不会出现「改了一半」的错位。

**3 座火箭发射台**：`(x+2,y+2)`、`(x+2,y-1)`、`(x-1,y)`

**3 个站位**（按 `unit_id` 末两位绑定，站位必须紧贴自己那座炮台）：

| `unit_id` 末两位 | 站位 | 操控的炮台 |
| --- | --- | --- |
| `10`（工人1） | `(x+1,y+2)` | `(x+2,y+2)` |
| `11`（开拓者） | `(x-2,y)` | `(x-1,y)` |
| `12`（工人2） | `(x+1,y-1)` | `(x+2,y-1)` |

**10 面城墙**（C 形：下沿 3 格 + 右列 6 格 + 上沿 3 格，两个角格共用）：

```
(x+1,y-2) (x+2,y-2) (x+3,y-2)
(x+3,y-1) (x+3,y) (x+3,y+1) (x+3,y+2) (x+3,y+3)
(x+2,y+3) (x+1,y+3)
```

**镜像**：基地 `x > 10` 时，以上所有坐标关于点 `(20, 15.5)` 中心对称，
即 `(X,Y) -> (40-X, 31-Y)`（也就是右下角那一方的布局）。
镜像时偏移取 `(1-dx, 1-dy)`：中心对称会把基地的「左下角」映到对面基地的
「右上角」，所以相对新基地左下角的偏移正好是 `(1-dx, 1-dy)`。

以上都是**写死的坐标**（`memory.py` 顶部的 `SLOT_LAYOUT` / `WALL_OFFSETS`），
不再做启发式选址。落点若不是合法空地只会告警并剔除，不会悄悄挪到别处。

## 白天分工（按角色）

1. **尾号 10 的工人 —— 10 石 → 10 墙 → 挖铁**
   - 到最近的石矿采 **10** 块石头（每回合 1 块）；
   - 回基地按上面写死的 10 个坐标砌墙（C 形护罩，开口背向敌人）；
   - 砌完后去挖 **铁矿**，卖给小贩；在「卖得掉 + 第 71 回合前回位」的前提下尽量多挖。
2. **尾号 12 的工人 —— 3 火箭 → 挖铜**
   - 开局的 75 金刚好够 3 × 25，先建满 3 座火箭；
   - 然后去挖 **铜矿**，卖给小贩，同样受「卖得掉 + 按时回位」约束。
3. **尾号 11 的开拓者 —— 2 个任务 → 商店门口等 BOSS 令**
   - `acceptTask` 领任务（全程站在任务点 1 格内，否则任务作废）；
   - 把任务原文交给 `prompt`（LLM），按回复决定是 `executeCmd` 进沙盒跑命令，
     还是 `submitAnswer` 交答案；命令输出会回灌给 LLM 继续推理；
     轮次用尽时把沙盒最后的输出兜底提交，绝不让任务空转到超时；
   - 两个任务做完后**直接去武器商店门口待命**：金币一到 200 立刻买、
     下一回合立刻 `use`，把「等钱」的时间压成 0；
   - 买到用完后立刻回位；若等不到 200 金就必须先回防（见下）。

> ⚠️ BOSS 召唤令是在**武器商店**（`weaponShop`）买的，不是小贩（`vendor`）。
> 小贩只收购矿石。所以开拓者待命的地点是武器商店门口；钱不够时它只站着等，
> **不会**发无效的 `buy`（买到买不起的东西属于指令非法，会计入队伍异常次数）。

### 两个矿种分开挖

`SLOT_ORE = {"10": 铁, "12": 铜}`：需求指定的分工，顺带让两人天然不抢同一个矿。
万一地图上该矿种全都不合适（太远 / 来不及），才退让到另一种矿，避免干站着。

### 采矿的时间预算与「尽早卖钱」

`_pick_mine` 不会选「跑不完的矿」：一次完整循环
（走到矿 → 采 N 块 → 走到小贩 → 卖 → 走回站位）必须能在归位截止前收尾，
否则降低 N（少采几块）或直接放弃。

另外有两条与 BOSS 令时点直接相关的规则：

- **矿一采空就立刻去卖**，不再顺路凑第二个矿。实测这一步把金币到 200 的时点
  从第 56 回合提前到第 40 回合，开拓者才有余量在归位前把卡买下来。
- **钱够了就停止挖矿**：金币除了买 BOSS 令没有别的用途，所以买完就收工回位。

## 夜晚（第 71~130 回合）

- 三个角色各守**自己槽位对应的那一座**火箭（10/11/12 末两位绑定，见上表）；
  开火要求角色与武器相邻、武器不在冷却（火箭冷却 3 回合）。
- **开火口径（需求）：射程内只要有「冲我们来的」敌人就打**，不攒齐射。
  「冲我们来的」= `targetTeam` 指向我方阵营的机器人（接口文档 1.5.1）：
  - 报文通篇没有这个字段时无法区分敌我走向，按全部视为威胁（宁可多打，不可漏防）；
  - 字段存在但没有任何一台指向我方，说明这波不是冲我们来的，一炮不发。
- **打谁**：目标集合里离我方基地最近的那台（不是离敌方基地最近）。
- **打哪一格**：按火箭伤害模型取单回合最大伤害——中心 20、周围 8 格各 10，
  并对「最靠近我方基地的那台」加权 2 倍，兼顾集火与最大化输出。
- **不浪费**：用「虚拟血量池」按火箭顺序结算已分配伤害，同一台机器人不会被两座塔
  重复打（第一座已计划击杀后，第二座自动改打别的目标）；射程内没有可打目标时保留冷却。

## 自测覆盖

`tools/smoke.py` 用 `docs/request.txt` 的地图搭了一个迷你裁判器（含矿井刷新、
小贩收购、商店价格、机器人夜晚推进、任务下发与 LLM 回复），九个场景全绿：

| 场景 | 校验点 |
| --- | --- |
| 样例矿价 + 任务 160 金 | 3 火箭 / 10 墙 / 2 任务 / 三人就位 / 金币过 200 并买用 BOSS 令 / 夜晚开火有效 |
| 高矿价 copper=25 | 矿价波动时同样走通整条链路 |
| 任务奖励低 (30/个) | 结构目标仍全达成，只是买不起 BOSS 令 |
| LLM 不作答 | 轮次用尽会兜底提交，2 个任务不白做 |
| 任务点延迟下发 | 第 1 回合 `playerTasks` 为空也要能补上，开拓者不能整天没任务 |
| LLM 不回包 | 等不到 `llmResp` 时必须兜底提交，不能僵在求解阶段 |
| 任务原文不下发 | 等不到 `phaseTask` 时补发一次 `acceptTask`，仍无则跳过该任务点 |
| roles 缺 health 字段 | 字段缺失不能被当成阵亡，否则全员都不被调度 |
| 镜像基地(右下角) | `x>10` 时整套布局确实是左下角布局的中心对称 |

结构断言不只是数数量，而是**逐格核对需求写死的坐标**：炮台必须是
`(x+2,y+2)/(x+2,y-1)/(x-1,y)`、城墙必须是那 10 格、10/11/12 结尾的角色必须站在
各自的专属站位上，并且**操控的必须是自己槽位对应的那座炮台**。
第 70 回合的快照同时就是第 71 回合的初始状态，所以这条断言等价于
「第 71 回合三人都已就位并能操控自己的炮台」。

### 报文解析的容错

报文是外部输入，字段偶尔缺失或类型不对，解析层必须扛住——一次解析异常
就会让**整个回合**拿不到任何指令。因此：

- 所有数值字段走 `as_int()`，转不了就用默认值，不抛异常；
- `roleType` / `neutralType` 走 `as_kind()`：去空白、容忍大小写，
  但**映回文档里的规范拼写**（不能简单转小写，否则 `weaponShop` 会变成
  `weaponshop` 而永远匹配不上）；
- `health` **缺失**时按存活处理（只有显式给 0 才算阵亡）。
  这条曾经是致命的：把缺失当 0 会让 `controllable()` 变成空集，
  于是所有角色都不再被调度，表现就是「开拓者一直没有动作」；
- 第一回合会把解析出的我方单位（id/kind/health）、可调度角色、任务点打进日志，
  并对未识别的 `roleType`、缺失基地、缺失 `playerTasks` 直接告警。

### 每回合的日志格式

每个回合都会把**完整的 Request 和完整的 Response** 写进日志，中间有明确分界线：

```
────────────── round 41 ──────────────
>>> REQUEST
{"roundNo": 41, "mapInfo": {...}, "teamOur": {...}}      ← 收到的原文，原样
<<< RESPONSE
{"roleCommandMap": {...}, "prompt": "", "executeCmd": ""}  ← 即将发出的原文
──────────────────────────────────────
```

日志是**逐字节机械**的：读到的正文原样写入，即将发出的字节原样写入，
不做缩进美化、不重新序列化——所以 `\uXXXX` 转义、多余空格、重复键、
浮点写法（`1.50`）在日志里都与链路上完全一致。

> `cmd` 只是 `roleCommandMap`。开拓者在「求解」阶段是靠顶层 `prompt` / `executeCmd`
> 干活的，那几回合它的角色指令本来就是空的——**只看 `cmd` 会误判成「开拓者没有动作」**。

日志详细程度由 `server.LOG_VERBOSITY` 控制，也可以用环境变量覆盖，不必改代码：

```bash
AGENT_LOG_VERBOSITY=digest bash run.sh <port>     # 只记关键字段
AGENT_LOG_VERBOSITY=off    bash run.sh <port>     # 不记报文
```

| 模式 | 一整天(130 回合)实测体积 | 内容 |
| --- | --- | --- |
| `full`（默认） | 约 562 KB | **原样**写入收到的 Request 与发出的 Response |
| `digest` | 约 145 KB | 只记 `roundNo/goldNum/phaseTask/llmResp/lastCmdResult/动作合法性/各单位位置背包/机器人数/errors`（**非原样**） |
| `off` | 约 0.4 KB | 只有启动与告警 |

十天比赛按 `full` 算约 5.5 MB。报文连 JSON 都解析不了时，会退化成记录原始字节前 500 字
（`请求体不是合法 JSON：b'...'`），并按容错规则回一个空指令响应。

排查时最直接的办法是拿日志里存下的报文跑一次诊断：

```bash
python3 tools/diagnose.py <那一回合的 request.json>
```

### 开拓者的防僵死设计

自进化任务本质是**跨回合问答**：本回合发 `prompt` / `executeCmd` / `acceptTask`，
下一回合才在 `llmResp` / `lastCmdResult` / `phaseTask` 里看到结果。
只要其中某一环不回包，朴素写法就会让开拓者永远停在「等待」状态、整局不再下发任何指令，
表现就是「开拓者没有行动」。因此这里有三层保护：

1. `LLM_WAIT_LIMIT = 3`：发出 `prompt` 后等不到 `llmResp`，就把沙盒最后的输出兜底提交；
2. `ACCEPT_WAIT_LIMIT = 3`：发出 `acceptTask` 后等不到 `phaseTask`，补发一次，仍无则跳过该任务点；
3. `TASK_STALL_LIMIT = 5`：任何阶段连续多回合毫无进展，一律放弃当前任务点转下一个。

放弃只跳过任务点、不计入完成数，所以既不会僵死也不会虚报任务数。
另外两条相关保护：任务点列表为空时会每回合重新补取（判题器可能第 1 回合还没下发）；
开拓者手上没任务时会自动转为可采购人员，不会白占一个角色。

`tools/mock_judge.py` 进一步做 HTTP 级联调：用 `bash run.sh <port>` 把程序拉起成独立进程，
通过真实 socket 逐回合 POST，并校验——

- 传输层：建连耗时 < 10s、单回合响应 < 5s（接口文档第 8 章）；
- 报文层：顶层 `roleCommandMap`/`prompt`/`executeCmd` 齐全、动作码合法、必填字段齐全、
  `targetPos` 为 `{x,y}` 数组、`controllerId` 为字符串、`num` 为整数、
  多目标武器的落点数等于当前等级；
- 语义层：指令指向的角色必须存在、操控者必须紧贴武器、`executeCmd` 只在任务期间下发；
- 健壮性：非法 JSON / 空对象 / 非根路径 POST 都不会让进程崩溃。

最近一次运行结果：130/130 回合完成，单回合往返平均 1.4ms、最大 12ms，
0 条协议错误、0 条语义告警，支持 keep-alive，进程全程存活。

## 已知边界

- **200 金够不够，取决于任务奖励。** 两个自进化任务按实际报文约给 160 金，此时
  样例收购价（石头 1 / 铁 3 / 铜 5）下也够用：初始 75 − 建塔 75 + 任务 160 + 一轮卖矿，
  第 40 回合金币过 200，第 46 回合买入、第 47 回合使用 BOSS 令。
  只有任务奖励也很低时（例如 `docs/request.txt` 字面写的 30/个）才凑不齐——
  那种局面下 70 回合的采矿上限约 110~140 金，代码会转为「尽量多赚、够了立刻买」，
  买不起就留作余额。若你希望此时改买武器升级券（100+150），说一声我加 fallback 分支。
- **BOSS 召唤令按任务书 4.6.3 是给对方加怪**（`对方下个夜晚 BOSS 机器人个数 +1`），
  不是给自己加。这里按需求照买照用。
- 任务答案只提交一次，答错不重试（时间预算优先留给「做完两个任务」）。
